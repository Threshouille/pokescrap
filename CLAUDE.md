# Pokescrap

Projet Unity (URP) : roguelike en temps réel, jouable à la manette, qui réutilise les assets et données de Pokémon Donjon Mystère sans chercher à reproduire le jeu d'origine (ex. : la carte est une grande arène carrée avec obstacles, pas un donjon à salles et couloirs). L'utilisateur parle français.

Conception : `Docs/GDD.md` (décisions d'Owen + points ouverts) ; le lire avant tout travail de gameplay et le tenir à jour quand une décision est prise. Reprise de session : `Docs/HANDOFF.md` (état, méthode de travail, problèmes connus).

## Économie de tokens
- Réponses courtes, pas de récapitulatif de ce qui vient d'être fait.
- Ne jamais lire `Library/`, `Temp/`, `Logs/` en entier ; pour un log, `grep`/`tail` ciblé.
- Ne pas lire les `.meta`, `.unity`, `.prefab`, `.asset` bruts : passer par les outils unityMCP.
- unityMCP : regrouper les opérations dans `batch_execute` ; paginer (`page_size`, `max_nodes`, `max_depth`) ; `generate_preview=false` ; `read_console` filtré sur les erreurs.
- Captures d'écran seulement si un contrôle visuel est nécessaire, en basse résolution (`max_resolution` ≤ 512).
- Scripts : `find_in_file` / `script_apply_edits` ciblés plutôt que relire le fichier complet.
- Pas de sous-agents sauf demande explicite.
- Données de jeu volumineuses (Pokémon, attaques) : les interroger par script (`jq`, Python), ne jamais les charger en entier dans le contexte.

## Données et assets issus de la ROM
- ROM : Explorateurs du Ciel EU (`C2SP`), `Rom/eos_eu.nds`, dépaquetée dans `Rom/files/` (hors `Assets/`, donc non importée par Unity).
- `python3 -I Tools/pmd/nds_unpack.py Rom/eos_eu.nds Rom/files` : dépaquette la ROM.
- `python3 -I Tools/pmd/extract_data.py Rom/files Assets/Data` : génère `pokemon.json`, `moves.json`, `types.json`, `abilities.json` (noms FR + `name_en`, identifiants = index internes du jeu).
- `Tools/.venv/bin/python -I Tools/pmd/extract_sprites.py Rom/eos_eu.nds Rom/export [first last]` (≈8 min pour tout, via `skytemple-files`) :
  - `Rom/export/sprites/<sprite_index sur 4 chiffres>/` : `AnimData.xml` + `<Anim>-Anim.png`, `-Offsets.png`, `-Shadow.png` (une ligne par direction, 8 directions) ; `sprite_index` vient de `pokemon.json`.
  - `Rom/export/portraits/<id Pokémon sur 4 chiffres>/<émotion>.png`.
- `Rom/export/` contient ~26 000 PNG : ne copier dans `Assets/` que les sprites réellement utilisés, jamais le dossier entier.
- `Tools/.venv/bin/python -I Tools/pmd/extract_tileset.py Rom/eos_eu.nds Assets/Tilesets <id>...` : décor de donjon → `Assets/Tilesets/<id>/chunks.png` + `tileset.json` (le décor 0 est un décor de test ; le 1 est utilisé dans la scène).
- Après ajout de fichiers : menus Unity **Pokescrap > Build Anim Sets** (sprites sous `Assets/Sprites/Pokemon/<Nom>/`) et **Pokescrap > Build Tilesets**.
- Scène : `Player` (`PlayerController` seul : crée les 3 Pokémon de l'équipe au lancement et suit celui que le joueur contrôle ; les autres ont `AllyAI`), `Dungeon` (`DungeonGenerator`, tilemaps `Floor` et `Walls` avec collisions), caméra avec `CameraFollow`. Les modifications de scène faites en mode Play sont perdues : vérifier `Application.isPlaying` avant d'éditer.
- Vitesse de base : absente de la ROM, lue dans `Tools/pmd/external/pokemon_stats.csv` (PokéAPI) par `extract_data.py`, qui écrit aussi `Assets/Resources/Data/pokemon_rt.json` (données compactes chargées en jeu).
- Combat (`Assets/Scripts/Combat/`) : `GameData` charge `pokemon_rt.json` et `realtime_moves.json` (attaques temps réel écrites à la main : famille, recharge, vitesse, portée, rayon, attaques de départ par Pokémon) ; `Combatant` (PV, attaques, recharges), `Projectile`, `EnemyAI`, `EnemySpawner`, `HealthBar`.
- Effets d'attaque : planches PNG (une ligne d'images, pointant vers la droite, 24 px = 1 case) + `effects.json` dans `Assets/Resources/Effects/`, faits avec Claude Design (originaux dans `Design/`). `EffectPlayer` les joue ; chaque attaque les référence par `effect` et `impactEffect` dans `realtime_moves.json`. Sans planche, un projectile retombe sur un disque coloré.
- `GameData` et `EffectLibrary` relisent leurs fichiers à chaque lancement de partie ; en mode édition (hors Play), leurs données peuvent être périmées tant qu'aucun script n'a été recompilé.
- Esquive : `Combatant.TryDodge` (traverse les adversaires, sans invincibilité, réglages `dodge*` dans `meta.json`). `DangerArea` (sur les annonces d'`EnemyAI`) et `Projectile.Threat` disent aux alliés quoi esquiver. Ennemis : `EnemySpawner.SpawnGroup` forme des `EnemyGroup` (cible commune, un soutien), rôle imposé via `GameData.RandomMoves(..., role)` / `CanTakeRole`. `EnemyAI` : pas de pause après l'attaque (`recoverTime` retarde seulement l'annonce suivante, `RoleTactics.Decide(..., canAttack: false)` donne le placement), esquive ennemie dans `EnemyAI.TryDodge` (`enemyDodgeCooldown`). Sortie de zone : `Zone.EscapeDirection` + `RoleTactics.EscapeStep` (murs seulement).
- Déplacement des IA : `Navigator` (A* sur la grille de `DungeonGenerator.Current`, zones nocives pénalisées via `Zone.Inside`). Toute nouvelle IA doit passer par `navigator.Direction(...)` plutôt que viser sa cible en ligne droite. `AllyAI` ne suit jamais le Pokémon joué dans un danger : il vise la case sûre la plus proche (`SafeSpotNear`, zone, terrain ou arc nocifs via `Dangerous`) par un chemin qui contourne les dangers (`navigator.Direction(..., avoid: true)` : cases dangereuses infranchissables, `Navigator.Dangerous` ; sinon chemin à surcoût et `SafePath` faux) et ne s'arrête au bord que sans chemin sûr. Cible des IA : `TargetChoice.Best` (score : K.O. possible via `Combatant.EstimateHit`, efficacité des types, menace sur un coéquipier, concentration via `TargetChoice.Note`, distance, maintien de la cible ; poids `aiTarget*` de `meta.json`), utilisé par `RoleTactics.Decide` et `EnemyGroup.Target`. `AllyAI` : suit le Pokémon joué qui recule (`allyFollowBreak`, `allyLeaderRetreatSpeed`), `allyAggroRange`/`allyLeash`, prudent sous `allyRetreatHealth` (reste près de lui, `allyCautiousAggro`).
- Familles d'attaques : `projectile`, `melee` (avec `lunge` éventuel), `zone` (aire persistante), `heal`, `modifier` (bonus/malus autour du lanceur, `target` : self / allies / enemies). Sur toute attaque : `status` (clé de `Assets/Resources/Data/statuses.json` : poison, paralysis, burn, sleep, freeze, confusion, trap, yawn, leech-seed ; `StatusLibrary` les lit, `Combatant.AddStatus` les applique), `modStat`/`modValue`/`modDuration`/`statChance` (malus à l'impact), `selfModStat`… (bonus au lanceur à l'impact), `drain`, `recoil`. Les contrôleurs passent leurs directions par `combatant.Steer(...)` (confusion) et `CurrentSpeed` vaut 0 quand un statut immobilise.
- Attaques génériques : `python3 -I Tools/pmd/generate_moves.py .` lit `moves.json` (ROM) et les CSV PokéAPI de `Tools/pmd/external/`, applique `Tools/pmd/move_rules.json` et écrit `Assets/Resources/Data/generated_moves.json` (+ `Tools/pmd/generated_moves_report.txt` : attaques écartées, à faire à la main). `GameData` charge les attaques générées puis celles de `realtime_moves.json`, qui gardent la priorité. Attention : dans la ROM, la plupart des attaques spéciales n'ont qu'une portée « devant soi » ; la famille vient donc aussi du drapeau de contact de PokéAPI.
- Attaques de base (`basic: true`) : une à distance (`basicByType`) et une au corps à corps (`meleeBasicByType`) par type dans `realtime_moves.json`, ou une ou plusieurs par Pokémon (`basicByPokemon`) ; `GameData.BasicMoves(id, style)` les donne, `GameData.StatStyle` choisit le style d'après Attaque / Attaque Spé (présélection du menu, ennemis). Elles sont en tête de `GameData.MovePool` (au choix dans le menu, apprenables en partie). Dégâts × `damageScale` ; ennemis : recharge × `enemyBasicCooldownMul`, dégâts × `enemyBasicDamageMul` (`meta.json`). Ignorées par `RoleFromMoves` (sauf si seules) et utilisées en dernier par `RoleTactics`.
- `castTime` (projectile et melee) : immobile, puis l'attaque part vers `Combatant.LiveAim` (visée actuelle du joueur, mise à jour par `PlayerController` ; nulle pour une IA) ; les tirs différés d'une rafale suivent aussi la visée. Projectiles : `path` (wave, zigzag, curve, orbit, arc, boomerang, homing) + `pathAmplitude`/`pathPeriod`, `burst`/`burstInterval` (+ `burstRoot` : immobile et sans attaque jusqu'au dernier tir, plus `recovery`), `sequential` (éventail tiré un par un : milieu, gauche, droite), `jitter`, `growth`, `accel`, `pierce`, `bounces`, `homing`, `effectScale`, `rangeStep`, `pulse`/`pulsePeriod` (taille qui oscille), `stun` + `stunChance`, `upright` (planche qui ne pivote pas), `endEffect` (planche jouée en fin de course, à la taille du tir), ruée avant le tir (`lunge`/`lungeTime`, sans dégâts : direction du déplacement, sinon la visée ; `count` tirs sur les flancs à `sideOffset`, qui attendent `hold` s puis partent vers l'ennemi ciblé au déclenchement : `Combatant.Shoot` / `FireFlankShots`, `Projectile.lockedTarget`) ; arc : `splash`, `puddle` + `puddleColor` ou `mark`/`markFrame`/`markFill` (planche au sol, `Shapes.Puddle`).
- Corps à corps (`Combatant.Melee` / `Strike`) : `shape` (circle par défaut, arc + `arc` (+ `sweep` : la planche tourne autour du lanceur à travers l'arc, dans un sens puis dans l'autre, `EffectPlayer.SpawnSweep`), thrust, around + `radiusMin`), `strikeOffset`, `hits`/`hitInterval`/`hitAngles` + `sideOffset` (coups qui partent des côtés et se croisent), `strikeEffect` (planche du coup d'une ruée ; une planche en boucle jouée par un coup s'arrête au bout de 0,3 s), `strikeRoot` (immobile et sans attaque jusqu'au dernier coup, `recovery` s'y ajoute), `step`, `chainBonus`/`chainMax`/`chainWindow` (planches `<effect>_2`, `_3`, multiplicateur affiché par `DamageNumber.Multiplier`), ruée `lunge` + `finishRadius`/`finishEffect`, `bounceBack`, `knockback` + `knockbackTime` (poussée qui ralentit), `lungeHarmless`, `lungeThrough` (traverse les adversaires), `delayedHit` (adversaires traversés frappés après la ruée), `strikeAfterLunge`/`strikeDelay` (le coup suit `LiveAim` au moment où il part), `hop`, `teleport` + `teleportDelay`/`trailEffect`, `recovery`, `stun` (sinon `meleeStun` de `meta.json`), `effectScale`. Cible du joueur : `PlayerController` choisit `Combatant.AimTarget` (`Combatant.FindAimTarget`, `aimCone`/`aimRange`/`aimDistanceWeight`/`aimKeepCone` dans `meta.json` ; la cible est gardée tant qu'elle reste dans `aimKeepCone`), dessine le cercle rouge (et le bleu sous le Pokémon joué) et met `LiveAim` vers elle ; `AutoAim` (tirs, avec anticipation), `MeleeAutoAim` et les zones s'en servent. Un tir `homing` du joueur poursuit sa cible. Zones : `firstTick` (délai du premier coup), `rootUntilHit` (adversaires figés jusqu'au premier coup), `target: "each"` + `areaRadius` (seulement les adversaires proches, cercle `Shapes.AreaRing`), `impactEffect` joué à chaque coup. Chaque coup au corps à corps avec dégâts appelle `Combatant.Stun` ; `Combatant.Knockback` pousse ; `IsHurt` force l'animation Hurt via `PmdAnimator.Forced`. Animations : les planches PMD « Attack » font avancer le sprite d'environ 0,85 case ; `GameData.AttackAnim` choisit l'animation jouée par les contrôleurs (`anim`, sinon Walk pour une ruée, Double pour un bonus `modifier` sur soi ou les alliés, Shoot, Attack) et `Combatant` impose `dashAnim` (Walk par défaut) pendant une ruée et `castAnim` pendant le lancement.
- Spores et poudres (Spore, Poudre Dodo, Para-Spore, Poudre Toxik, Spore Coton) : `castTime` 0,5 puis 6 nuages (`count` 6, `spread` 300) qui grossissent (`growth`, jusqu’en fin de course : 1,5 case à 1,75 case/s) et traversent (`pierce`) ; planches `<clé>_spore` / `_impact` / `_fin` (originaux : `Design/effects_v10_spores/`, prompt `Design/prompt_spores.md`).
- Boss : `BossAI` (ajouté par `EnemySpawner` à la place d'`EnemyAI`) tire une attaque au hasard et l'annonce par une bulle numérotée (`Shapes.NumberBubble`), sans zone de danger. Familles ajoutées pour eux : `burst` (dégâts autour du lanceur), zones à dégâts (`power` > 0), zone `target: "each"` (une sous chaque adversaire), projectiles multiples (`count`, `spread`).
- Rôles (`melee`, `ranged`, `support`) : déduits des attaques équipées par `GameData.RoleFromMoves` (soin ou bonus aux alliés → soutien ; projectiles et zones au moins aussi nombreux que le contact → distance ; sinon corps à corps), recalculés à chaque attaque apprise. Le champ `role` de `loadouts` ne sert plus qu'aux boss ; `loadouts` donne aussi les attaques de départ par défaut. `RoleTactics.Decide` choisit l'attaque et le déplacement pour `AllyAI` comme pour `EnemyAI`.
- Importer un Pokémon : `python3 -I Tools/pmd/import_pokemon.py . Nom=id ...` (sprites, portrait, `id.txt`), puis menu Build Anim Sets, puis l'ajouter à `loadouts`.
- Tous les Pokémon de la ROM sont importés (`Tools/pmd/import_all_pokemon.py .` : une entrée par numéro de Pokédex + les 28 Zarbi, saute ceux déjà présents). Formes alternatives et versions de l'histoire écartées : `Docs/POKEMON_EXCEPTIONS.md`, à revoir au cas par cas. Build Anim Sets sur tout le roster sature la mémoire de l'éditeur ouvert : le lancer de préférence en batch (`python3 Tools/setup.py --unity-only PmdSpriteImport.BuildAll`, éditeur fermé : trouve Unity seul, journal dans `Logs/setup_unity.log`).
- Attention : dans la ROM, les attaques apprises suivent l'index de `monster.md`, pas son champ « entity id » (identiques seulement jusqu'à 201). Icônes d'effets : planche `status_<clé>` dans `Assets/Resources/Effects/` si elle existe (clés : les 9 statuts de `statuses.json`, `attack_up`, `attack_down`, `defense_up`, `defense_down`, `speed_up`, `speed_down`), sinon icône de secours dans `Shapes`. `Combatant.GetEffects` liste les effets actifs.
- Déroulé d'une partie : liste `stages` sur l'objet `Enemies` (`EnemySpawner`) ; chaque étape a un nom, un décor (`DungeonTileset`), un niveau d'ennemis, des vagues et éventuellement un boss. Entre deux étapes : fondu, `generator.Generate()` avec le nouveau décor, `PlayerController.PrepareForNextArena`. `EnemySpawner` dessine aussi l'indicateur d'étape, la barre du boss et les écrans de fin.
- Salles (`feature/salles`, étape 1 du GDD « Étages et salles ») : `RoomCatalog.Pick(type, rng)` tire dans `Assets/Resources/Data/rooms.json` (types → thèmes → variantes, tailles, décors par n° de la ROM) un `RoomInstance` ; `DungeonGenerator.room` (sinon arène carrée classique) : taille rectangulaire centrée dans la grille carrée (`Interior`), plan `RoomLayouts.Apply` (open, blocks, pillars, cross, ring, bars, maze ; zones coupées du départ murées), décor `TilesetRoster.Get(n°)` (`Assets/Resources/Data/Tilesets.asset`, rempli par Build Tilesets), obstacles de la variante via `Obstacles.GenerateArena` avec `decorKind` (liquide dessiné par le décor). `JsonUtility` crée les objets absents : un `RoomLayout` sans style = ouvert, un type ne remplace le plan que si son `layout.style` est rempli. Galerie : salle 3 de `TerrainSandbox` (escalier vert). Contrôle : `python3 Tools/setup.py --unity-only RoomCheck.Run` → `Logs/rooms_preview.png` ; captures réelles `Unity -batchmode -projectPath . -executeMethod RoomShots.Run -quit` (sans `-nographics`) → `Logs/rooms_shots.png` : à regarder après tout changement de décor ou de variante. Liquide : `theme.liquid` (water, lava, void) dessiné par la couche secondaire du décor seulement pour `liquidDecors` (sinon aspect standard). Rochers : `Obstacles.Draw` prend `ObstacleTiles/rock_<décor de la salle>` s'il existe (extraits par `setup.py` pour tous les décors de `rooms.json`, `rocks.core` / `rocks.none`), sinon `romRocks`. Salle vide alors que la variante a des obstacles : `Generate` recommence (6 fois). Hors partie, `Obstacles`/`Terrain`/`Pylons` détruisent par `Discard` (DestroyImmediate). Décors de la ROM : seuls 0-169 sont des décors (`dungeon<n>.dma`) ; liste donjon → décor : voir `Docs/HANDOFF.md`.
- Île (GDD « L'île flottante », remplace les niveaux continus comme structure de la run ; ceux-ci serviront aux chaînes d'îlots) : `IslandPlan.Generate(rng)` (données par case : `region` = quartier 0-3, `Centre`, `Moat`, `Border`, `Void` ; `biome` = `IslandPlan.SubBiome` ; `altitude`/`moisture` classés par quartier ; `themes[4]`, `order` (sens horaire), `start`). Réglages `island.json`, thèmes et sous-biomes `biomes.json` (plages d'altitude et d'humidité, décors, couleur d'aperçu, `peak`). La graine est brassée (`System.Random` donne des premiers tirages proches pour des graines proches). Grands éléments (`IslandFeatures.cs`, partie de `IslandPlan`) : `obstacle[]` (clé d'obstacles.json) et `wall[]` par case, `passages` (`IslandPlan.Passage` : une extrémité `a` dans la zone `from`, `b` dans `to`, contre leurs murs ; quartier → quartier suivant, dernier quartier → centre ; `Arrival(zone)`), cratère, lacs, rivières (pente générale vers la côte + altitude + méandre, ponts tous les `BridgeEvery`), falaises (lignes de niveau `cliffLevels`, trous par bruit), massifs (`walls` par sous-biome, bruit classé), `Connect` (par quartier, tout atteignable depuis `Arrival(q)` : chemin le plus court à travers murs et obstacles, petites poches murées). Aperçu : `IslandCheck.Run` → `Logs/island_preview.png`. Zones séparées : une seule zone construite à la fois (`DungeonGenerator.islandZone` : quartier 0-3 ou `IslandPlan.Centre`, `islandArrival`, `IslandOrigin` : case de l'île de `Interior.min`), rectangle `ZoneBounds(zone)` ; le reste (autres zones, barrières, fossé) = mur, la côte = ciel ; `IslandRun.Build(zone, arrivée)`, marqueurs des extrémités de passage, `LoadingScreen.Run(titre, chargement)` (écran noir, `Time.timeScale` à 0) ; retour possible ; mini-carte = zone actuelle, brouillard gardé pour toute l'île. Rendu (étape 3) : `DungeonGenerator.island` (avant `level` et `room`) → `GenerateIsland` : `cellDecor[]` (décor par case : celui du sous-biome, `IslandPlan.DecorOf`, sinon celui de la terre la plus proche, centre = décor 45), `skyWall[]` (ciel au bord de la côte : tuile invisible à collider), dessin par lots (`SetTiles`), cache de tuiles par (décor, morceau, solide) ; obstacles posés case par case (`Obstacles.Place`, la rivière sous le pont), fossé = vide. `IslandFeatures.DecorEdges` : haie d'une case là où le décor change (trous par bruit). `IslandRun` : lancement, ciel (fond de caméra), mini-carte avec brouillard, `Quarter`/`Biome` sous le Pokémon joué ; île de test = salle 4 de `TerrainSandbox` (escalier orange). Performances sur l'île : `Navigator` borné (4 000 cases par recherche, budget de 4 000 par image partagé par toutes les IA), `ObstacleTactics.Repair` local (`RepairRange` 40, 5 000 cases) ; scénario « Île » du banc (mesure immobile / course sans IA / course avec IA). Étapes suivantes : îlots, sceaux et engrenages, centre, rencontres.
